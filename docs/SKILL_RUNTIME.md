# Universal Skill Runtime V1

> 这一版做的是「外部 Skill 零配置导入与运行」。
> 一句话：**你在别的 Agent 里用顺手的 Skill，导入后应该直接能用**，不需要研究 Python、Node、依赖、路径或环境。

---

## 1. Skill 是什么

Skill 就是一个「让 AI 按某套固定方法干活」的小包裹。它可能是：

- 一份 Markdown 提示词（最简单，教 AI 怎么分析和输出）；
- 一份带输入输出结构说明的规则包；
- 一段 Python 或 Node 脚本（能真正计算、读文件、生成表格）；
- 上面几种的组合。

它和「一句提示词」的区别是：Skill 是一套可复用、可重复、带规则和示例的完整方法。

---

## 2. Skill 怎么导入

打开左侧 **Skill** 页面 → 右上角 **导入 Skill**，支持四种方式：

| 方式 | 适合 |
| --- | --- |
| 单个 .md / .txt / .json / .yaml 文件 | 纯提示词型 Skill |
| 选择文件夹 | 带脚本、示例、资料的完整 Skill |
| 拖拽文件夹进来 | 同上，更快 |
| zip 压缩包 | 从 GitHub / 别的工具导出的包 |

点击后你只会看到两句提示：**「正在准备 Skill…」** → **「可使用」**。

---

## 3. 什么叫「零配置」

意思是：**技术兼容问题不需要你处理**。系统在后台自己完成识别、适配、装环境、装依赖、映射工具、自检、修错。

你不会看到，也不需要理解：缺哪个包、要哪个版本的运行时、路径怎么写、工具名怎么对应、格式差在哪。

---

## 4. 后台自动做了什么

导入一个 Skill 时，系统按顺序做这些事（全部静默）：

1. **识别**：扫描所有文件，判断这是提示词型、结构型，还是带 Python / Node 代码的类型；找出主说明文件、示例、输入输出结构。
2. **归一化**：把五花八门的外部格式，统一成 Director 内部的 Skill 描述（Manifest）。
3. **保留原件**：原始文件原封不动存一份，以后升级 Runtime 可以重新适配。
4. **准备隔离环境**：需要 Python 就建独立虚拟环境，需要 Node 就建独立依赖目录，**互不影响，也不影响平台本身**。
5. **装依赖**：自动读 requirements.txt / pyproject.toml / package.json，也自动从代码里的 import 推断。
6. **映射工具**：把外部工具名（read_file / Read / filesystem.read…）统一映射成平台内部能力。
7. **静默自检**：真实跑一次最小验证。
8. **自动修复**：自检失败先尝试自动修，最多 3 次。
9. **登记**：只有自检通过，才会变成「可使用」。

---

## 5. Skill 怎么进入 AI 对话

在 Skill 页面点某张卡片的 **使用** → 自动跳到 **AI 对话** → 顶部出现 **已启用：Skill 名称 ×** → 直接说话即可。

**已经在用的 AI 对话没有被另起一套**。Skill 只是挂到当前这个会话上。

---

## 6. Installed 和 Active 的区别（很重要）

- **Installed（已安装）**：Skill 页面里所有的 Skill。
- **Active（当前启用）**：只有你在这个会话里点了「启用」的那 1–3 个。

平台**不会**把所有已安装 Skill 都塞给 AI —— 那只会让回答变慢、变贵、规则互相打架。所以：

- 装 50 个 Skill，AI 也只会看到你当前启用的那几个；
- 一个会话最多同时启用 3 个；
- 关掉某个 Skill（点胶囊上的 ×）只影响这个会话，不会卸载它。

---

## 7. Skill Runtime 是什么

Runtime 是「让 Skill 真正能跑起来」的那层。它负责加载 Skill、准备环境、提供工具、执行、管超时、管错误、返回结果。

可以把它理解成：**Skill 是菜谱，Runtime 是厨房**。菜谱来自哪里不重要，厨房保证做得出菜。

---

## 8. Python / Node 如何隔离

每个需要代码的 Skill 都有**自己的独立环境**：

- Python：`<数据目录>/skills/<skillId>/runtime/python/`（独立虚拟环境）
- Node：`<数据目录>/skills/<skillId>/runtime/node/`（独立依赖目录）

所以：Skill A 要的依赖版本和 Skill B 冲突也没关系；也**绝不会**改动平台自己的依赖。

平台明确禁止：使用 sudo、全局 pip install、修改系统 Python、污染主项目 package.json。

---

## 9. Tool Adapter 如何工作

外部 Skill 写的工具名各不相同：`read_file`、`Read`、`filesystem.read`、`file_reader`…平台内部只认一套能力表（例如 `file.read`）。

中间靠一张**别名映射表**转换。新增一种 Agent 的命名习惯，只需要往表里加一条别名，**不用改 Runtime**。

如果某个外部工具平台确实没有对应能力（比如联网搜索、图片理解），系统会**如实标注「暂时无法使用」**，不会假装能跑。

---

## 10. Silent Verification 是什么

导入完成 ≠ 安装完成。

系统会在后台真实跑一次最小验证，例如：提示词型 Skill 会真调一次模型确认指令能生效；带脚本的 Skill 会真实启动隔离环境、真实加载依赖、真实执行一次入口。

**只有验证通过，界面才显示「可使用」。** 验证过程你看不到日志，只会看到「正在准备」。

---

## 11. 自动 Repair 是什么

第一次自检失败，不代表 Skill 不能用。系统会先按失败原因自动修，再重新验证：

| 失败现象 | 自动处理 |
| --- | --- |
| 缺 Python 包 | 自动安装缺的那个包并重试 |
| 缺 Node 包 | 自动安装缺的那个包并重试 |
| 找不到入口文件 | 重新扫描整个 Skill，重新识别入口 |
| 工作目录被改坏 | 重建隔离目录 |
| 工具名认不出来 | 用别名表重新映射一次 |

最多尝试 3 次。修不好才会标记为「暂时无法使用」，并且**原始文件、失败原因、日志全部保留**，以后平台能力升级可以「重新验证」，不需要你重新找文件。

---

## 12. 什么情况下必须你授权

只有**真正属于你的账号或密钥**才需要你参与，例如：

Notion / 飞书 / Google / 抖音 / 小红书授权、你自己的付费 API Key、企业内部权限、外部 MCP 凭证。

这类 Skill 会被准确标记为 **「需要授权」**，平台**不会伪造任何密钥**。

技术问题（缺包、缺运行时、路径、工具名、格式差异）永远由系统处理 —— 这两件事不会混在一起。

---

## 13. 如何扩展支持新的 Agent Skill 格式

只需要在 `src/lib/skills/tool-mapping.ts` 的别名表里加一条：

```ts
{
  capability: "file.read",     // 平台内部能力
  adapter: "sandbox-file-read",// 用哪个适配器
  aliases: ["读文件", "load_file"],   // 这个 Agent 的叫法
  patterns: [/^myagent\.read$/i]
}
```

识别逻辑本身（`analyzer.ts`）是按「文件名 + 文件内容 + manifest + package + 源码 + 说明文档」综合判断的，不依赖固定目录结构，所以新格式通常不加代码就能识别。

---

## 14. 出问题以后开发者应该看哪里

| 想看什么 | 位置 |
| --- | --- |
| 一个 Skill 的完整过程日志 | `GET /api/skills/<skillId>/logs`，或 `<数据目录>/skills/<skillId>/logs/runtime.log` |
| 归一化后的内部描述 | `<数据目录>/skills/<skillId>/manifest.json` |
| 原始文件（永不被改写） | `<数据目录>/skills/<skillId>/original/` |
| 隔离环境 | `<数据目录>/skills/<skillId>/runtime/` |
| 平台能力表 | `src/lib/skills/capability-registry.ts` |
| 工具别名表 | `src/lib/skills/tool-mapping.ts` |
| 可调参数（超时/重试/上限） | `src/lib/skills/config.ts` |

数据目录 = `DIRECTOR_RUNTIME_DIR`（桌面版是 App 的 userData），本地开发默认是项目下的 `.director-platform-data/`。

普通用户界面永远不显示这些内容。

---

## 15. 这一版的边界（没做的部分）

- 不做 Skill 商店 / 评分 / 社区 / 排行榜。
- 不做 AI 创建 Skill（架构上留了位置，本期不实现）。
- 不做复杂可视化工作流编辑器。
- 联网搜索、网页抓取、图片生成/理解、资产读写这几项能力**只登记、不自动执行**：依赖它们的 Skill 会被标成「暂时无法使用」，而不是假装能跑。
- 第三方授权只做「准确识别」，不做授权中心。

这些都不是「没做」，而是**刻意划定的边界**：先把「导入即可用」这条主链路做扎实。

---

## 16. 测试与验收

```bash
npm run test:skill-runtime        # 导入 → 准备 → 自检 → 自动修复 → 真实执行（不需要 Electron）
npm run test:skill-chat           # Skill 中心 → 使用 → AI 对话 → 规则生效 → 关闭（需要 Electron）
```

`test:skill-runtime` 覆盖 7 个 Fixture：纯 Markdown、Python、Node、工具映射、缺依赖自动修复、需要授权、平台无此能力。当前结果：**15/15 通过**。

`test:skill-chat` 用真实 Electron 页面 + 真实模型跑完整交互链：Skill 中心出现 → 点击使用 → 跳转 AI 对话 → 顶部挂载 → **回答里出现该 Skill 独有的指纹（证明规则真的生效）** → 关闭后指纹消失 → 多 Skill 共存 → 关闭其一另一个保留。当前结果：**8/8 通过**。
